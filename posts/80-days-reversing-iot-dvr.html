80 Days Reverse Engineering an IoT DVR:
What I Found and Why It Didn't Work Out

Chin Yi Zhe (@cyeezy08) · September 2026 · 10 min read

Most vulnerability research writeups read like flawless action movies: the researcher looks at a binary, finds a 0-day in an afternoon, writes a slick exploit, cashes a bounty check, and walks into the sunset.

This is not that writeup.

I spent roughly 80 days digging through stripped ARM32 firmware binaries powering tens of thousands of white-label OEM surveillance DVRs globally. I extracted bootloader sequences, broke hardcoded crypto, uncovered an unauthenticated root firmware execution vector, and hooked dynamic functions in QEMU.

And at the end of it all? I had zero bounty payouts, no live remote shell on the physical target, and an orphaned vulnerability.

Here is the technical reality of what I found, the tools and shims I built, and the harsh lessons I learned about target selection in offensive security.

TL;DR: I reverse-engineered a widely deployed HiSilicon Hi3521a-based OEM surveillance DVR platform. I found a genuine protocol auth bypass (hardcoded AES-256 keys) and an unsigned root upgrade execution chain. But the live firmware build lacked a remote wire dispatch path, the white-label vendor has no disclosure program, and exploit brokers like ZDI only purchase bugs for enterprise brands. Here is the post-mortem.

1. The Target: OEM HiSilicon Surveillance Hardware

The hardware under test was a widely deployed digital video recorder built on the HiSilicon Hi3521a SoC (ARM32) running an embedded Linux kernel. These units are mass-produced by OEM manufacturers in East Asia and white-labeled under dozens of brand names.

The firmware ships with a custom management daemon that listens on TCP port 8000 (often called the DNP / NetSession service) alongside an embedded web interface. The core logic lives in stripped proprietary shared libraries (e.g. libdal.so) and custom binaries (gui-indus-3r, S90dvrd). 

# Extracted firmware environment
CPU Architecture : ARMv7 Processor rev 1 (v7l) - ARM32 little-endian
SoC Target       : HiSilicon Hi3521a
Daemons          : S90dvrd (boot orchestration), gui-indus (Qt-based event loop)
Shared Library   : libdal-indus-hi3521a.so (demux & protocol dispatcher)

2. What I Found: Legitimate Vulnerabilities

Finding 1: Authentication Bypass via Hardcoded AES-256 Seeds

The proprietary binary protocol on port 8000 uses an 8-byte header: magic=0x5AA5, cmd (uint16), and length (uint32).

During disassembly in Ghidra, I analyzed the login sequence (command 0x8100). To my surprise, authentication does not rely on a secret credential exchange. Instead, the device uses a static AES-256-CBC key and static IV hardcoded into the .rodata section of both libdal and the GUI binary: 

KEY = b"dvr1234567!@#$%^&*()QWERTYUIOP%".ljust(32, b"\x00")
IV  = b"123456789012345\x00"

# Command 0x8100 Login Handshake:
# 1. Payload is double-AES encrypted using the static key.
# 2. Server accepts the frame and immediately returns a valid session token.
# 3. Subsequent commands are encrypted using the returned session string.

I verified this handshake live over the network: sending the double-AES encrypted frame resulted in an immediate session_id issuance without ever supplying valid administrative credentials.

Finding 2: The Unsigned Root Firmware Upgrade Flow

Next, I audited the boot scripts and firmware update logic. In S90dvrd (the init boot script), I spotted this sequence: 

FWR=/dvr/fwr
if [ -f "$FWR" ]; then
    tar -zxvf $FWR ./upgrade
    chown root /dvr/upgrade
    chgrp root /dvr/upgrade
    chmod 755 /dvr/upgrade
    /dvr/upgrade $FWR reboot &
fi

Notice what is completely absent: cryptographic signature verification. There is no GPG verification, no public-key signature check, and not even a hash validation. If an archive containing an executable named ./upgrade is written to /dvr/fwr, the device unpacks it and executes it directly as uid=0 (root) during boot.

Finding 3: Command Injection via sscanf Parsing

In older firmware images of this generation, opcode 0x220 handled firmware staging. It parsed incoming command strings using a format string: 

sscanf(payload, "fname:%s size:%d ver:%s", &src_path, &file_size, &version);

The first token (src_path) was later passed directly into a system() call: 

mv %s /dvr/fwr.tmp

The firmware had a command gate function at 0x9cc70 that audited the input string before passing it to the shell. The gate rejected only two characters: backticks (`) and dollar signs ($). It completely permitted semicolons (;), pipe characters (|), and redirects (>).

Because semicolons were unblocked, a crafted input like: 

fname:/dev/null;id>/tmp/pwned;# size:1 ver:1.2.3.4

bypassed the gate entirely and executed arbitrary commands under the server's context.

3. The Tooling & Emulation Setup

To research this without bricking the physical hardware, I built a local emulation and analysis lab:

  • Static Analysis: Ghidra for decompiling ARM32 binaries and mapping cross-references; radare2 for fast symbol lookup and rodata pattern searching.
  • Dynamic Emulation: QEMU user-mode (qemu-arm-static) inside an ARM64 Linux environment (Raspberry Pi 5 and GitHub Codespaces).
  • Custom Hook Shims: Wrote LD_PRELOAD shims hooking strcmp and strncmp to extract internal opcode dispatch tables from memory.
  • Wire-Faithful Stubs: Created Python socket emulators that faithfully mirrored the exact byte-level framing, double-AES encryption, and session crypto.

In the local sandbox, the entire exploit chain worked end-to-end: authentication bypass → opcode dispatch → injection → root marker written.

4. Why It Didn't Work Out: The Real-World Wall

So why am I writing a post-mortem instead of a CVE announcement with a bounty screenshot?

1. The Delivery Path Gap

On real, modern firmware builds running on the live hardware, the vendor had modified their internal DNP dispatch table. While opcodes 0x8100 (login) and 0x0120 (device info) replied perfectly, sending 0x220 or 0x221 caused the unit to close the TCP connection with zero bytes returned.

The underlying unsigned /dvr/upgrade root execution flaw was still physically in the binary. The static AES keys were still physically in memory. But the network delivery trigger over DNP was dead on this build. Without a delivery mechanism, you don't have an exploit; you only have an architectural critique.

2. The White-Label Orphan Problem

In bug bounty programs (HackerOne, Bugcrowd), you get paid because a corporation takes responsibility for their software.

In the OEM IoT world, nobody takes responsibility. The company that manufactured the HiSilicon board sold it to a vendor in Shenzhen, who flashed a custom GUI, sold it to a trading company, who rebranded it to a dozen third-party camera labels. There is no security team. There is no security@ email. There is no bug bounty program.

3. The Commercial Exploit Broker Reality (ZDI)

I attempted to submit the research to the Zero Day Initiative (ZDI).

ZDI operates a legitimate, well-paying commercial marketplace for 0-day vulnerabilities. But their purchase criteria are dictated by enterprise demand. ZDI buys vulnerabilities that affect major vendors (Microsoft, Apple, VMware, Cisco, Adobe) because those are the systems that protect enterprise networks.

A white-label OEM DVR from an obscure hardware vendor has zero commercial enterprise resale value. My submission was denied.

5. What 80 Days Taught Me

Spending 80 days on a project that yields $0.00 in revenue will either break you or sharpen you. For me, it forced me to grow:

  1. Target Selection is 80% of the Battle: Never sink months of vulnerability research into a hardware platform or codebase unless you already know who has the authority, budget, and incentive to fix it or pay for it.
  2. Skills Compound Independently of Bounties: Even though the target was a commercial dead-end, I mastered ARM32 assembly, QEMU chroot debugging, cryptographic protocol reversing, and embedded Linux boot sequences. Those skills are permanently banked in my brain.
  3. Honesty Over Hype: It would have been easy to exaggerate my findings and claim a "Critical Remote 0-Day RCE on 28,000 devices." But real security researchers respect intellectual honesty. Admitting where an exploit chain falls short is what builds genuine technical reputation.
